# Runbook: API + worker on Render (free), database on Neon, media on Cloudflare R2, web on Vercel

```
browser ──> Vercel (web) ──/api/*──> Render (API + worker, one free service) ──> Neon (PostgreSQL)
                         └─/media/*─> Cloudflare R2 (images)
```

`render.yaml` describes one free web service that runs the **API and the worker together**
(`scripts/render-start.sh`): Render's free plan has no background workers. The script applies the database
migrations, starts both processes, and exits (so Render restarts it) if either one dies.

## 1. Accounts and services (all have free plans; check current limits)
1. **Neon**: create a project (region Singapore if offered). Copy the **direct** connection string (not the pooled one), it ends with `?sslmode=require`. The `unaccent` extension used by the migrations is supported.
2. **Cloudflare R2**: create bucket `nona-media`, allow public read through a public bucket URL (or a custom domain). Create an API token with read+write on that bucket: you get the endpoint `https://<account>.r2.cloudflarestorage.com`, an access key and a secret. R2 cannot make only some prefixes public, so the whole bucket is readable by anyone who knows an object URL. Keys contain random UUIDs (not guessable) and the web `/media` proxy only forwards `products/`, `articles/` and `custom/`; customers' design files (`designs/`) are only served by the API to their owner. For stricter isolation use a second private bucket for `designs/` (needs a code change).
3. **SMTP** for email (any provider with a free tier and port 587).

## 2. Render
1. *New → Blueprint*, pick this repository: it reads `render.yaml`. (Or create a Web Service by hand with the same build/start commands.)
2. Fill in every variable marked `sync: false`:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon direct URL |
| `WEB_ORIGIN` | exact Vercel origin, e.g. `https://nona.vercel.app` (no trailing slash) |
| `API_PUBLIC_URL` | the service URL Render gives, e.g. `https://nona-api.onrender.com` |
| `MEDIA_BASE_URL` | `<WEB_ORIGIN>/media` |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | from R2 (`S3_REGION=auto`) |
| `MFA_ENCRYPTION_KEY` | `openssl rand -base64 32` |
| `VNPAY_*` | from the VNPay merchant portal |
| `ZALO_*`, `ZALO_ZNS_TEMPLATE_ID` | see `zalo-otp-setup.md` |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` | from the SMTP provider |

   `INTERNAL_API_TOKEN` and `OTP_SECRET` are generated by Render. `NODE_ENV=production` makes the API **refuse the payment and SMS simulators** and require the VNPay, Zalo, MFA and OTP settings above. To test without them, set `NODE_ENV=development`, `PAYMENTS_MODE=simulator` and `SMS_MODE=simulator` (cookies are then not `Secure`: demo only).
3. Deploy. Watch the log for `database is up to date`/`applied: ...`, then `worker started` and `api listening`. Health check: `GET /v1/health/live`, readiness (with the database): `/v1/health/ready`.
4. Create the first staff account once, from your machine: `NONA_STAFF_PASSWORD='a-long-password' DATABASE_URL='<neon url>' pnpm --filter @nona/database exec tsx src/cli.ts create-staff you@example.com ADMIN "Your name"`. Never run `db:seed` against this database.

## 3. Vercel
Follow `deploy-vercel.md` with `INTERNAL_API_URL=https://nona-api.onrender.com`, `MEDIA_ORIGIN=<R2 public bucket URL>/` (no trailing slash) and `SITE_URL`. Then make sure `WEB_ORIGIN` on Render is the final domain and redeploy Render.
VNPay IPN address: `https://nona-api.onrender.com/v1/webhooks/payments/vnpay`.

## 4. Free-plan behaviour to expect
- **The service sleeps** after a period without requests; the next request takes about a minute while it wakes up. While it sleeps the worker does not run either (emails and OTP codes wait). A free uptime monitor that pings `https://nona-api.onrender.com/v1/health/live` every 5 minutes keeps it awake (check Render's terms; the 750 free hours cover one service running all month).
- **Memory is 512 MB** for the API and worker together (about 250 MB used at rest). Image processing (previews, uploads) peaks higher: keep uploads small. If the service is killed for memory, upgrade the plan.
- Build memory on the free plan is limited. If `pnpm install` or `nest build` is killed, retry once; otherwise upgrade for the build.
- **Neon scales to zero** too: the first query after a long idle takes a moment.
- Logs are kept only briefly: check them soon after problems.

## 5. Updating
Push to `main`; Render rebuilds and the start script applies new migrations before the API starts (migrations are checksummed and idempotent). Roll back by redeploying the previous commit in Render (do not edit applied migrations).
