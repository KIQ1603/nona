# Security review — Phase 5 (payments, refunds, coupons, MFA)

Scope: code and configuration added in Phase 5, reviewed against `references/security-operations.md`. Status: ✅ done · ⚠ accepted risk / follow-up · ❌ open.

| #   | Area                          | Finding / control                                                                                                                                                                                                                                                                        | Status                                          |
| --- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 1   | Webhook authenticity          | HMAC-SHA512 verified (timing-safe) before anything else is read; merchant code checked; amount compared with our own payment row; tampering returns 97/04/99 and changes nothing. Tests cover forged hash, forged amount, wrong merchant, array-parameter tricks.                        | ✅                                              |
| 2   | Replay / duplicates           | Events deduplicated in `payment_events` (unique key) under a row lock; concurrent identical IPNs settle exactly once (tested with 6 parallel).                                                                                                                                           | ✅                                              |
| 3   | Redirect trust                | Return page ignores `vnp_*` result params; order page shows server-verified state only; polling instead of trusting the redirect.                                                                                                                                                        | ✅                                              |
| 4   | Money correctness             | Integer VND everywhere; totals/discounts computed server-side and re-computed inside the order transaction; `expectedTotalVnd` mismatch → 409. DB CHECKs keep totals consistent.                                                                                                         | ✅                                              |
| 5   | Overselling                   | Variant rows locked in id order, availability read in a **separate** statement (a first version oversold under concurrency; fixed + regression tests).                                                                                                                                   | ✅                                              |
| 6   | Late / duplicate payments     | Late payment after expiry or cancellation: accepted only if stock remains, otherwise auto-refund; double payment of one order → second refunded.                                                                                                                                         | ✅                                              |
| 7   | Refund safety                 | Append-only table + trigger; capacity checked under lock; sent to provider at most once (`attempted_at`); uncertain outcome → manual, audited resolution; permission `refunds:write` only.                                                                                               | ✅                                              |
| 8   | Coupons                       | Admin-managed data; evaluated server-side under a lock on the coupon row (usage limits race-tested); rule snapshot stored per order; apply endpoint rate-limited (20/15 min/IP); no stacking.                                                                                            | ✅                                              |
| 9   | Staff authentication          | TOTP (RFC 6238 vectors tested) with replay protection, encrypted seeds (AES-256-GCM), hashed one-time recovery codes, attempt lock (5), challenge token signed + 5-minute expiry; `REQUIRE_STAFF_MFA` restricts every admin route until enrolment; MFA cannot be disabled when required. | ✅                                              |
| 10  | Internal endpoints            | Worker/metrics endpoints need `INTERNAL_API_TOKEN` (timing-safe); respond 404 when unset or wrong.                                                                                                                                                                                       | ✅                                              |
| 11  | Simulator                     | Refused by environment validation when `NODE_ENV=production`; routes 404 outside simulator mode.                                                                                                                                                                                         | ✅                                              |
| 12  | Secrets                       | Production boot fails without provider credentials, internal token and a 32-byte MFA key; nothing secret in logs (callbacks log txnRef only).                                                                                                                                            | ✅                                              |
| 13  | Rate limiting                 | Login, sign-up, order lookup, password reset, coupon apply, MFA attempts limited — **in memory**.                                                                                                                                                                                        | ⚠ move to Redis before >1 API replica (Phase 7) |
| 14  | Client IP                     | Rate limits use `req.ip`; the web server forwards `X-Forwarded-For`; in production the edge proxy must overwrite it (otherwise spoofable).                                                                                                                                               | ⚠ document in deployment (Phase 7)              |
| 15  | VNPay field list              | Adapter follows the published 2.1.0 contract; query/refund request and response signing was verified against our own simulator only.                                                                                                                                                     | ⚠ **verify against live sandbox before launch** |
| 16  | Refund of uncertain outcome   | Requires human follow-up by design; alerting via `/admin/system`, metric and worker log.                                                                                                                                                                                                 | ⚠ staff runbook exists                          |
| 17  | CSP / security headers on web | Basic headers only.                                                                                                                                                                                                                                                                      | ⚠ Phase 7                                       |
| 18  | Dependency scan               | CI runs `pnpm audit`; not yet gating on this phase's new packages.                                                                                                                                                                                                                       | ⚠ Phase 7                                       |

No ❌ items. Items marked ⚠ are tracked in `docs/ROADMAP.md` (Phase 7) or are launch-gate checks.
